# Grievances — ledger of non-blocking findings

> Committed register of underlying problems, technical debt and improvements met
> **outside the scope of an in-flight spec**: "what works, but will not scale, or
> only holds together with tape". Committed on purpose — friction should
> accumulate visibly.
>
> **This file is maintained programmatically.** Declare and close entries with the
> `grievances` skill CLI; never hand-edit the index tables below:
>
> ```bash
> grievances.py add --short "..." --severity high --locus "file.go:42" \
>   --finding "..." --impact "..." --fix "..." --effort 0.5d
> grievances.py resolve GRV-0001 --commit 1a2b3c4 --note "..."
> ```
>
> Prose under `# Details` is human-owned and kept verbatim; the heading lines, the
> `<!-- grievance:... -->` markers and both tables belong to the tool, which
> re-sorts them chronologically on every mutation.
>
> **Boundary.** Anything regulatory, security-related, data-losing or needing an
> arbitration does NOT stay here: it becomes a spec, or a fiche in the pilot
> `ROADMAP.md`, immediately — close the grievance with `--promoted-to <ref>` so a
> one-line pointer remains and the analysis lives in exactly one artifact.
>
> Never paste a secret, a token or a credential-bearing log line into an entry:
> record the *command* that retrieves a credential, never its value.
>
> When to read and when to write: `specs/CLAUDE.md`.

### GRV-occurrences-counter-loses-1aa4 · medium · 2026-08-26 — occurrences counter loses an increment when two branches both bump

`skills/grievances/scripts/grievances.py:cmd_bump` · declared in spec 015 adversarial review, deferred by design · tags: `grievances`, `merge-safety`

<!-- grievance:GRV-occurrences-counter-loses-1aa4:prose -->

**Finding.** `occurrences` is an int that `bump` increments. Two branches bumping the same grievance from 2 both write 3; the merge keeps one 3, so the true count of 4 is lost. Same class as the identifier collision spec 015 fixed, and untouched by it.

**Impact.** The counter is the ledger's only frequency signal and the tie-breaker for what gets promoted to a spec. Silently undercounting makes a recurring papercut look like a one-off, which is exactly the entry most worth promoting.

**Why the tests miss it.** Spec 015's suite covers identifier collisions across branches; nothing exercises a concurrent bump, because a unit test sees one ledger at a time and the loss only appears at merge.

**Fix.** Replace the integer with an append-only list of recurrence dates, which merges by union rather than by last-write-wins. Also improves the record: when a finding recurred is more useful than how often. **Effort: 0.5d.**

### GRV-stale-cached-container-reported-aa46 · high · 2026-09-16 — A stale cached container id is reported to the agent as a lint violation, and validation then stops silently

`skills/static-validation-hooks/templates/validate-on-edit.sh:246`

<!-- grievance:GRV-stale-cached-container-reported-aa46:prose -->

**Finding.** exec_in caches the resolved container id under STATE_DIR and takes a hot path that runs docker exec on it with no lookup. Its recovery from a stale id is keyed on exit code 125, and the comment at line 246 states the assumption: '125 = no running container (or docker unusable)'. That assumption is false for docker exec. Measured on Docker via OrbStack, 2026-09-16: 'docker exec -i <missing-id> echo hi' exits 1, both for a container id that existed and is gone and for a bogus id; 125 is what the CLI returns for its own usage errors, such as an unknown flag on docker run. So the stale-cid branch at lines 259-264 never fires, the cache file is never removed, and rc=1 falls through the 124/125/126/127 arms of check() into the default arm, which sets _VIOLATION and feeds the captured output to the agent.

**Impact.** Two harms at once, and both defeat a promise the skill makes explicitly. First a false failure: the agent is told the edited file has a validation violation whose text is 'Error response from daemon: No such container: <id>', when nothing was linted. The 124, 125 and 126/127 arms all return 0 precisely so an infrastructure problem never masquerades as a finding; the most likely infrastructure problem takes none of them. Second, silence: the cache is only cleared inside the 125 branch, so every later edit in that project repeats the same failure, the files are never validated, and an agent that has seen the noise twice starts ignoring the hook. Observed 2026-09-16 in modelo-broker-pa worktree 197-convx-impl, where a Claude subagent reported the hook failing twice with that exact daemon error and fell back to running the linter by hand. Five real lint findings in code written during that batch survived to the end of the session and were caught only by an explicit final pass.

**Why the tests miss it.** Nothing exercises exec_in against a container id that has ceased to exist. The cache lives in TMPDIR keyed on the project root, so it outlives any stack recreation, and a test that resolves and execs in one run never reaches the state the hook spends most of its life in.

**Fix.** Treat the stale cid by what it is rather than by an exit code the CLI does not produce: on any non-zero rc from the cached-id attempt, drop the cache and re-resolve once before deciding, or verify the id with 'docker inspect' when the exec output matches 'No such container'. Whichever route, the 125 contract at line 246 should be corrected in the comment too, since it is the assumption the three degradation arms are built on. **Effort: 0.5d.**

### GRV-routing-table-ships-factory-e300 · medium · 2026-09-16 — No Go routing table ships with the factory, so every Go consumer rediscovers the vendoring trap

`skills/static-validation-hooks/routing/`

<!-- grievance:GRV-routing-table-ships-factory-e300:prose -->

**Finding.** The factory ships routing/python.sh, routing/typescript.sh and routing/nestjs.sh. There is no routing/go.sh, so a Go consumer writes its own. Measured in modelo-broker-pa on 2026-09-16: that repository vendors its dependencies, and the Go linter invoked without GOFLAGS=-mod=mod exits with 'inconsistent vendoring in /app' listing every module, before analysing a single file. With the flag the same command returned 5 real findings in that branch's own code.

**Impact.** A routing table written without that flag does not report a clean file; it reports an error that never names a line, so a reader concludes the tool ran and found nothing. That is the failure the skill exists to prevent, arriving through the one stack the skill has no opinion about. It is also knowledge each Go consumer pays for separately, which is what a routing table is for.

**Why the tests miss it.** The routing tables are shipped examples, not executed code, and none of the three existing ones targets a language whose default module mode can fail before analysis.

**Fix.** Add routing/go.sh with the flag set, the standard Go linter as check, gofmt as fix, and a comment stating why the flag is not optional in a vendored module. The Python and TypeScript tables are the model. **Effort: 0.5d.**

`skills/static-validation-hooks/SKILL.md` · declared in hook-factory hardening session 2026-09-17

<!-- grievance:GRV-static-validation-hooks-skill-da25:prose -->

**Finding.** Three copies are live: this repo (source, installed by install.sh), ~/.claude/skills/static-validation-hooks (installed 2026-09-08, behind on the Cursor postToolUse fix), and ~/code/claude-flow/plugins/claude-flow/skills/static-validation-hooks (ahead: covers/policy verbs, --capabilities v2, 343 lines vs 300). **Impact.** A fix written here does not reach the consumer that reported the defect, and a fix written in the plugin never returns upstream. **Fix.** Decide which tree owns the skill, make the other two derived (install.sh for the installed copy, a scripted refresh or a symlink for the plugin), and reconcile the current delta first: Cursor postToolUse text upstream-only, covers/policy + --capabilities plugin-only. **Effort: 0.5d.**

`skills/.DS_Store` · declared in adversarial-review-convergence skill creation
