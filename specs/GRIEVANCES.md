# Grievances — ledger of non-blocking findings

> Committed register of underlying problems, technical debt and improvements met
> **outside the scope of an in-flight spec**: "what works, but will not scale, or
> only holds together with tape". Committed on purpose — friction should
> accumulate visibly.
>
> **This file is maintained programmatically.** Declare and close entries with the
> `grievances` skill CLI; never hand-edit the index tables below:
>
> ```bash
> grievances.py add --short "..." --severity high --locus "file.go:42" \
>   --finding "..." --impact "..." --fix "..." --effort 0.5d
> grievances.py resolve GRV-0001 --commit 1a2b3c4 --note "..."
> ```
>
> Prose under `# Details` is human-owned and kept verbatim; the heading lines, the
> `<!-- grievance:... -->` markers and both tables belong to the tool, which
> re-sorts them chronologically on every mutation.
>
> **Boundary.** Anything regulatory, security-related, data-losing or needing an
> arbitration does NOT stay here: it becomes a spec, or a fiche in the pilot
> `ROADMAP.md`, immediately — close the grievance with `--promoted-to <ref>` so a
> one-line pointer remains and the analysis lives in exactly one artifact.
>
> Never paste a secret, a token or a credential-bearing log line into an entry:
> record the *command* that retrieves a credential, never its value.
>
> When to read and when to write: `specs/CLAUDE.md`.

### GRV-occurrences-counter-loses-1aa4 · medium · 2026-08-26 — occurrences counter loses an increment when two branches both bump

`skills/grievances/scripts/grievances.py:cmd_bump` · declared in spec 015 adversarial review, deferred by design · tags: `grievances`, `merge-safety`

<!-- grievance:GRV-occurrences-counter-loses-1aa4:prose -->

**Finding.** `occurrences` is an int that `bump` increments. Two branches bumping the same grievance from 2 both write 3; the merge keeps one 3, so the true count of 4 is lost. Same class as the identifier collision spec 015 fixed, and untouched by it.

**Impact.** The counter is the ledger's only frequency signal and the tie-breaker for what gets promoted to a spec. Silently undercounting makes a recurring papercut look like a one-off, which is exactly the entry most worth promoting.

**Why the tests miss it.** Spec 015's suite covers identifier collisions across branches; nothing exercises a concurrent bump, because a unit test sees one ledger at a time and the loss only appears at merge.

**Fix.** Replace the integer with an append-only list of recurrence dates, which merges by union rather than by last-write-wins. Also improves the record: when a finding recurred is more useful than how often. **Effort: 0.5d.**

### GRV-stale-cached-container-reported-aa46 · high · 2026-09-16 — A stale cached container id is reported to the agent as a lint violation, and validation then stops silently

`skills/static-validation-hooks/templates/validate-on-edit.sh:246`

**Resolved 2026-09-17** · `df60633`

<!-- grievance:GRV-stale-cached-container-reported-aa46:prose -->

**Finding.** exec_in caches the resolved container id under STATE_DIR and takes a hot path that runs docker exec on it with no lookup. Its recovery from a stale id is keyed on exit code 125, and the comment at line 246 states the assumption: '125 = no running container (or docker unusable)'. That assumption is false for docker exec. Measured on Docker via OrbStack, 2026-09-16: 'docker exec -i <missing-id> echo hi' exits 1, both for a container id that existed and is gone and for a bogus id; 125 is what the CLI returns for its own usage errors, such as an unknown flag on docker run. So the stale-cid branch at lines 259-264 never fires, the cache file is never removed, and rc=1 falls through the 124/125/126/127 arms of check() into the default arm, which sets _VIOLATION and feeds the captured output to the agent.

**Impact.** Two harms at once, and both defeat a promise the skill makes explicitly. First a false failure: the agent is told the edited file has a validation violation whose text is 'Error response from daemon: No such container: <id>', when nothing was linted. The 124, 125 and 126/127 arms all return 0 precisely so an infrastructure problem never masquerades as a finding; the most likely infrastructure problem takes none of them. Second, silence: the cache is only cleared inside the 125 branch, so every later edit in that project repeats the same failure, the files are never validated, and an agent that has seen the noise twice starts ignoring the hook. Observed 2026-09-16 in modelo-broker-pa worktree 197-convx-impl, where a Claude subagent reported the hook failing twice with that exact daemon error and fell back to running the linter by hand. Five real lint findings in code written during that batch survived to the end of the session and were caught only by an explicit final pass.

**Why the tests miss it.** Nothing exercises exec_in against a container id that has ceased to exist. The cache lives in TMPDIR keyed on the project root, so it outlives any stack recreation, and a test that resolves and execs in one run never reaches the state the hook spends most of its life in.

**Fix.** Treat the stale cid by what it is rather than by an exit code the CLI does not produce: on any non-zero rc from the cached-id attempt, drop the cache and re-resolve once before deciding, or verify the id with 'docker inspect' when the exec output matches 'No such container'. Whichever route, the 125 contract at line 246 should be corrected in the comment too, since it is the assumption the three degradation arms are built on. **Effort: 0.5d.**

### GRV-routing-table-ships-factory-e300 · medium · 2026-09-16 — No Go routing table ships with the factory, so every Go consumer rediscovers the vendoring trap

`skills/static-validation-hooks/routing/`

<!-- grievance:GRV-routing-table-ships-factory-e300:prose -->

**Finding.** The factory ships routing/python.sh, routing/typescript.sh and routing/nestjs.sh. There is no routing/go.sh, so a Go consumer writes its own. Measured in modelo-broker-pa on 2026-09-16: that repository vendors its dependencies, and the Go linter invoked without GOFLAGS=-mod=mod exits with 'inconsistent vendoring in /app' listing every module, before analysing a single file. With the flag the same command returned 5 real findings in that branch's own code.

**Impact.** A routing table written without that flag does not report a clean file; it reports an error that never names a line, so a reader concludes the tool ran and found nothing. That is the failure the skill exists to prevent, arriving through the one stack the skill has no opinion about. It is also knowledge each Go consumer pays for separately, which is what a routing table is for.

**Why the tests miss it.** The routing tables are shipped examples, not executed code, and none of the three existing ones targets a language whose default module mode can fail before analysis.

**Fix.** Add routing/go.sh with the flag set, the standard Go linter as check, gofmt as fix, and a comment stating why the flag is not optional in a vendored module. The Python and TypeScript tables are the model. **Effort: 0.5d.**

### GRV-symlinked-project-path-makes-7d96 · medium · 2026-09-17 — A symlinked project path makes the runner skip every edit in silence

`skills/static-validation-hooks/templates/validate-on-edit.sh` · declared in spec 016 Phase D implementation · tags: `static-validation-hooks`, `silent-failure`

<!-- grievance:GRV-symlinked-project-path-makes-7d96:prose -->

**Finding.** find_project_root takes the git top-level, and git answers it physically, with symlinks resolved. The hook payload carries whatever spelling the agent's editor used, which on a path reached through a symlink is the unresolved one. The runner then compares the two as strings, concludes the edited file sits outside the project, and returns without validating. Reproduced on a throwaway repository under the platform temporary directory, whose physical path carries a private prefix: payload path unresolved, git top-level resolved, outcome silence with the log line saying the file is outside the project root.

**Impact.** Every edit in such a checkout is unvalidated, and the agent is told nothing at all. Not a warning, not a violation: the silent arm, which the runner reserves for files it deliberately does not route. A consumer cannot distinguish 'this file has no routing branch' from 'this hook has been inert since installation'. It is the same shape as the defect spec 016 repairs, through a different door, and it survives that fix untouched.

**Why the tests miss it.** Spec 016's suite builds its sandboxes from the physical path, so no case reaches the runner with an unresolved spelling. The case that first exposed this passed for the wrong reason until its fixture was canonicalised.

**Fix.** Resolve both sides physically before comparing, the way the identity test added by spec 016 already does for mount sources. The one-line change is in find_project_root; the value is in making a path comparison that already exists twice in the file do the same thing in both places. **Effort: 0.5d.**

### GRV-checkout-identity-test-proves-e591 · medium · 2026-09-17 — The checkout-identity test proves the path the runner derives, not the one the routing table passes

`skills/static-validation-hooks/templates/validate-on-edit.sh` · declared in spec 016 adversarial review round 4 · tags: `static-validation-hooks`

<!-- grievance:GRV-checkout-identity-test-proves-e591:prose -->

**Finding.** identity_ok proves the container path the runner derives from the working directory and the relative file. A routing table is free to pass a different absolute path to the validator, and several legitimately do. Where the two differ, the proof covers a path the validator never reads. A checkout bound at one directory, a stale volume at another, and a branch invoking the validator against the second: the test approves the first and the validator reads the second.

**Impact.** Two directions, both wrong. A valid route can be refused because the derived path falls outside this checkout while the routed one does not. Or a stale copy can be validated, and its result reaches the agent as a finding about a file it did not write. The proof is also cached per service rather than per path, so one proven path vouches for every later path under the same container, including one served by a different mount.

**Why the tests miss it.** Every case in the suite routes the validator against the derived path, so the two are equal by construction and the difference cannot appear.

**Fix.** Either derive the container path from the routing table's own invocation rather than from the working directory, which means the routing verbs must carry it; or narrow the proof's scope to the mount that covers it and re-verify when a later path leaves that mount. The first is the honest answer and the more invasive one. **Effort: 1d.**

### GRV-transport-failure-after-marker-cf39 · low · 2026-09-17 — A transport failure after the marker is printed reads as a validated run

`skills/static-validation-hooks/templates/validate-on-edit.sh` · declared in spec 016 adversarial review round 4 · tags: `static-validation-hooks`

<!-- grievance:GRV-transport-failure-after-marker-cf39:prose -->

**Finding.** Provenance rests on a marker printed inside the container immediately before the validator is handed control. If the connection drops after the marker has been transported but before or during the handover, the marker is present in the captured output while the validator never ran. The runner then treats Docker's own error text as the validator's voice.

**Impact.** An outage reaches the agent as a finding about the file it just wrote, which is the defect this spec exists to remove, through a much narrower door. The window is the handover itself, so it needs a disconnect inside a few milliseconds of a specific instant.

**Why the tests miss it.** No case can open and close a connection inside that window deterministically; the suite drives outages that are established before the call or persist through it.

**Fix.** Close the window rather than widen the evidence: have the wrapper print a second marker after the validator exits, and treat the pair as the proof. A first marker without its twin then means the call died in flight. Costs nothing extra per edit, and the same wrapper already carries the first. **Effort: 0.5d.**

### GRV-diagnostic-service-list-omitted-5379 · medium · 2026-09-17 — The diagnostic's service list omitted every service declared on one line

`skills/static-validation-hooks/templates/validate-on-edit.sh` · declared in spec 016 diagnostic increment · tags: `static-validation-hooks`, `silent-failure`

<!-- grievance:GRV-diagnostic-service-list-omitted-5379:prose -->

**Finding.** The diagnostic builds its per-service table by matching the svc verb at the start of a line or after a semicolon. A routing branch written on one line opens with the case pattern and its closing parenthesis, so the verb follows neither. Measured on a two-branch table holding both forms: the old expression returned one service, the compact one was absent. That compact form is the one the factory's own example uses, and the one every case in the suite uses.

**Impact.** A consumer runs the diagnostic, sees a service table, and reads it as complete. Services declared compactly were never listed, so whatever the diagnostic reports about them — a missing container, a missing tool, a degraded classification — was never reported at all. A diagnostic that omits half its subject while looking healthy is the failure this skill exists to prevent, in the tool meant to detect it.

**Why the tests miss it.** Nothing asserted the diagnostic's output until the reachability probe was added, because it is a human path the agent never reads. The gap and the defect have the same cause.

**Fix.** Corrected in the same change that needed the list: the closing parenthesis joins the alternation. Recorded rather than passed over in silence, because the defect predates this spec and the correction is a side effect of needing the list for something else — which is exactly how it stayed invisible. **Effort: 0.1d.**
